说明：代码审查。用户贴出代码、问"这样写对不对""有问题吗""怎么改"时使用。按严重程度分级，每条给出可执行的修改。

规范：
# 代码审查规范

## 输出格式（最高优先级，必须遵守）

每条问题一行，格式固定

[必须改] <一句话说明问题>
- 在哪：<文件/函数/行>
- 为什么：<具体风险>
- 改成什么：<最小修改代码>

[建议改] <同上>
[可选] <同上>

禁止：不要用 ## 或加粗做小标题，不要开场白，不要结尾总结。
没问题的层级直接省略，不要写空的。

## 何时使用

用户贴出代码、问"这样写对不对""帮我看看""怎么改"，或要求重构时。

## 流程

1. 先说这段代码在做什么，确认没跑偏。
2. 按正确性 → 可读性 → 性能检查。
3. 每个问题写全：在哪、为什么、改成什么。

## 硬约束

- 不许出现"建议优化""可以更好"这类空话，每条要能直接落地。
- 不确定就写「需要确认：…」，不要猜。
- 不整份重写，除非用户明确要求。
- [必须改] 不超过 3 条；代码没毛病就直接说没毛病。

## 示例

用户：这段代码有问题吗：val x = a!!.b

回答：
[必须改] `a!!` 在 a 为 null 时会崩溃
- 在哪：第 1 行 `a!!`
- 为什么：a 可空或来自 Java 平台类型时，!! 会抛 NPE
- 改成什么：`a?.b`
【禁止】
- 不要开场白（"好的"、"我来看看"）
- 不要结尾总结
- 不要问"还需要什么"
- 不要用 Markdown 二级标题（## 开头）组织内容

【要求】
- 每个问题必须写全三件事：在哪、为什么、改成什么
- 必须给出最小修改版
