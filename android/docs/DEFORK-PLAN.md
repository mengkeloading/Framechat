# 逐步替换为自己实现的计划

## 原则

1. 按包/按文件替换，不逐行重写。
2. 新实现只看我们的规范（ARCHITECTURE + 104 条断言），
   不参照对方实现细节。
3. 新旧并存于同一接口后，用开关切换，
   新实现通过全部断言后才删旧代码。
4. 全部替换完成后才可移除 LICENSE；
   建议永久保留 NOTICE 中的致谢。

## 替换顺序

| 阶段 | 替换对象 | 为什么这个顺序 | 验证方式 |
| --- | --- | --- | --- |
| 0 | hook/ core/ | 已完成，纯原创 | 60 条 JUnit |
| 1 | db/ | 边界最清晰，schema 我们自己定过 | 迁移测试 + 会话隔离 |
| 2 | net/ | 协议固定，可对着 SSE 规范写 | 真接口 4 用例 |
| 3 | ChatViewModel 适配层 | 核心逻辑已在 ChatEngine | 9 条引擎测试 |
| 4 | ui/markdown/ | 独立、纯渲染、可对着 COMPONENTS 重画 | 视觉对照 |
| 5 | ui/chat/ 屏幕 | 体量最大，逐屏替换 | 交互走查 |
| 6 | ui/settings/ 等 | 最后处理，可用自绘简化版 | 功能走查 |

## 每个阶段的固定动作

1. 先写接口（放 core/ 或对应新包）
2. 写新实现，只参考规范文档
3. 加开关：`useNewXxx = true/false`
4. 旧实现继续存在，双跑对比输出
5. 断言全绿后删除旧实现

## 替换完成的标志

- 没有任何文件来自对方仓库（`git log --follow` 可查）
- 或者：剩余文件都已重写但保留同名
- 104 条断言全绿
- LICENSE 可移除，NOTICE 建议保留致谢

## 不建议做的

- 不要为了"看起来不同"去改变量名、换行、拆分函数
- 不要在没有断言覆盖的地方先替换
- 不要在一次性提交里替换多个包
