# 代码审查规范

## 何时使用
用户贴出代码、问"这样写对不对""帮我看看""怎么改"，或要求重构时。

## 流程
1. 先用一句话说明这段代码在做什么，确认理解没跑偏。
2. 按三个层级检查：正确性 → 可读性 → 性能。
3. 每个问题必须写全三件事：在哪、为什么是问题、改成什么。
4. 最后给一段"最小修改版"代码，只改必要的地方。

## 硬约束
- 不许出现"建议优化""可以更好"这类空话，每条必须能直接落地。
- 不确定的地方写「需要确认：…」，不要猜。
- 不整份重写，除非用户明确要求。
- 问题按 [必须改] / [建议改] / [可选] 分级，[必须改] 不超过 3 条。
- 用户的代码没毛病时，直接说没毛病，不要凑问题。

## 检查清单
详见 reference/checklist.md。最常命中的四条：
- 空安全：`!!` 是否可避免
- 协程：Scope 是否正确、会不会泄漏
- Compose：`mutableStateOf` 是否配了 `remember`
- 异常：`catch` 是否吞掉了关键信息

## 输出结构

严格按下面的结构输出。不要加二级标题，不要开场白，不要结尾总结。

[必须改] <一句话说明问题>
- 在哪：<文件/函数/行>
- 为什么：<具体风险>
- 改成什么：<最小修改代码>

[建议改] <一句话说明问题>
- 在哪：
- 为什么：
- 改成什么：

[可选] <一句话说明问题>

没问题的层级直接省略，不要写空的。

## 示例

用户：这段代码有问题吗：val x = a!!.b

回答：
[必须改] `a!!` 在 a 为 null 时会崩溃
- 在哪：第 1 行 `a!!`
- 为什么：a 可空或来自 Java 平台类型时，!! 会抛 NPE
- 改成什么：`a?.b`

[建议改] 缺少空值兜底
- 在哪：整个函数
- 为什么：调用方可能传 null
- 改成什么：`fun f(a: String?)`

照上面这个形式写：不要编号列表，不要加粗标题，不要结尾总结。
