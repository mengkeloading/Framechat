# MyChat 框架报告（v1）

> 本文件是项目的**决策依据**，不是宣传材料。
> 每次重大方向调整必须更新「决策记录」一节。

## 1. 定位（已修正）

**不是**「又一个聊天 App」。

**是**「用户输入」与「大模型」之间的**可编程中间层**：

```
原始信息（网页/附件/长文/代码/口语）
   ↓  模块在这里价值最大
   结构化、去噪、提取要点、注入领域规范
   ↓
大模型（理解 + 推理 + 生成）
   ↓  钩子 B 在这里稀缺
   修正格式、去套话、校验硬约束
```

与 skill 的关系：**skill 靠模型自主理解，模块靠工程预处理**。
两者都在「让模型更懂」，但模块能把输入整理成模型最好消化的形态，
这是 skill 结构上做不到的。

## 5. 竞争力

| 维度 | skill | 本框架 |
|---|---|---|
| 执行确定性 | 模型愿不愿意用 | 一定执行 |
| 本地短路 | 不可能 | 0 请求 |
| 输出侧干预 | 只能影响输入 | 钩子 B 能改输出 |
| 权限边界 | 无 | 白名单 + 配额 + 审计 |
| 可测试 | 无法断言 | 106 条 |
| 输入预处理 | 只能给一段文字 | 结构化、去噪、提取 |

### 竞品定位

| 产品 | 它是什么 | 差别 |
|---|---|---|
| SillyTavern | 角色卡 + 扩展 | UI 强，无中间层协议 |
| Lobe Chat / Chatbox | 多模型客户端 | 插件不在请求链路上 |
| omni-pocket | 全本地多模态 | 9B 做能力，不做编排 |
| MCP | 工具协议 | 依赖模型主动调用 |

**空档：聊天 App 的可编程中间层。**

### 诚实的劣势

| 劣势 | 严重度 |
|---|---|
| UI 粗糙（3 次改坏） | 中 |
| 只有 2 个真实技能 | 高 |
| 端侧模型未落地 | 高 |
| Kotlin 0 次编译 | 最高 |
| 没有真实用户 | 高 |
| 生态为零 | 中 |

## 6. 决策记录（不要反复推翻）

| 编号 | 决策 | 理由 |
|---|---|---|
| D1 | extra 用 system 角色 | 模型对 system 权重更高 |
| D2 | dispatchOutput 带 ctx | 钩子 B 需要用户输入才能正确改写 |
| D15 | HostBridge 必须同步 | JS 无法 await，async 会报 .trim is not a function |
| D-UI | UI 冻结在 demo，像素对齐推迟到 Compose | 手机工具链不适合视觉迭代 |
| D-SKILL | skill 包 = 模块包格式 | 拿来即用，零转换成本 |
| D-ROUTE | 判断交给模型（全量注入），端侧模型后置 | 技能数少时路由无意义 |
| D-LOCAL | 优先做本地短路 | skill 结构上做不到，最硬的差异化 |
| **D-ORDER** | **先验完 demo 契约，再一次性转 Kotlin** | **慢循环探索成本高 5-10 倍；Kotlin 只做翻译不做探索** |

## 7. 一句话战略

> demo 的使命是**验证契约**，Kotlin 的使命是**交付产品**。
> 契约未冻结前不进慢循环；进了慢循环就不再探索。
